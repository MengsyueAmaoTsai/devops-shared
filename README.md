# devops-shared

Shared Azure Pipelines version template and IIS deployment script for RichillCapital.

This repository does not produce a deployable application. Service repositories reference the
version template through an Azure Pipelines repository resource and execute the shared deployment
script directly.

## Contents

| Path | Purpose |
|---|---|
| `.azure-pipelines/stages/version.yml` | Calculates SemVer using GitVersion |
| `scripts/iis/Deploy-IisSite.ps1` | Provisions IIS and deploys ASP.NET Core or Node applications |
| `PSScriptAnalyzerSettings.psd1` | PowerShell static analysis rules |
| `tests/Deploy-IisSite.Tests.ps1` | Pester static analysis tests for the deployment script |
| `.github/workflows/validate.yml` | Linting and tests for this repository |

## Referencing the repository

Declare the repository in the consumer's `azure-pipelines.yml`:

```yaml
resources:
  repositories:
    - repository: devops-shared
      type: github
      name: MengsyueAmaoTsai/devops-shared
      endpoint: github_MengsyueAmaoTsai
      ref: refs/heads/master
```

`@devops-shared` must match the `repository` alias. If a consumer is pinned to
`refs/heads/master`, changes to `master` directly affect subsequent pipeline runs. Pinning a
version tag is recommended for production environments.

## Calculating the version

```yaml
stages:
  - template: .azure-pipelines/stages/version.yml@devops-shared
    parameters:
      gitVersionVersion: '6.0.5'
```

The template creates `VersionStage` and `ComputeVersionJob`. Downstream stages can read the output:

```yaml
variables:
  version: $[stageDependencies.VersionStage.ComputeVersionJob.outputs['setVersion.semVer']]
```

The template updates the Azure Pipeline build number with the calculated SemVer. The consumer must
retain the complete Git history. To customize versioning rules, provide a `GitVersion.yml` file in
the consumer repository.

## Deploying to IIS

`Deploy-IisSite.ps1` provisions the IIS infrastructure and deploys the application in the same
workflow:

- Creates or reconciles the application pool, website, HTTP binding, and firewall rule.
- Configures permissions for the site and `logs` directories.
- Accepts either a publish output directory or a `.zip` file.
- Checks the health endpoint after deployment and automatically rolls back on failure.

All provisioning steps are idempotent: the first deployment to a clean host and the hundredth
deployment follow the same path. Manually changed application pool settings are reconciled during
the next deployment.

### Hosting model

`-HostingModel` determines which process runs the application. Both models share the rest of the
deployment workflow.

| | `AspNetCore` (default) | `ReverseProxy` |
|---|---|---|
| Runner | IIS worker process through the ASP.NET Core Module | Windows service registered by WinSW |
| IIS role | Hosts the application directly | Holds the external binding and rewrites requests to loopback |
| Payload marker | `web.config` | `-ServerEntryPoint` |
| Environment variables | `ASPNETCORE_ENVIRONMENT` is set on the application pool | `NODE_ENVIRONMENT` and other values are written to the service definition |
| Supported `Mode` values | `InPlace`, `Swap` | `InPlace` only |

`ReverseProxy` additionally requires `-NodePort`, which must differ from `-Port`. `-Port` is the
external IIS port, while `-NodePort` is the port on which the Node process listens over loopback.
The latter is not opened in the firewall.

`-ServerEntryPoint` serves as both the service entry point and the payload marker. Its name differs
by framework and must match the root structure of the payload published by the service:

| Framework | `-ServerEntryPoint` | Payload root |
|---|---|---|
| Next (standalone) | `server.js` (default) | `.next/standalone/`, with `.next/static` and `public` copied back |
| Astro (Node standalone) | `server/entry.mjs` | `dist/` |
| Nuxt (Nitro) | `server/index.mjs` | `.output/` |
| Angular (SSR) | `server/server.mjs` | `dist/<project>/` |

`Swap` is explicitly rejected for `ReverseProxy`. Swap points the site to a version-specific
directory, but a Windows service has only one working directory and one registered image path.
The two would become disconnected: IIS could point to the new version while the service continued
running the old version, allowing the health check to pass against the wrong version.

### Environment configuration is not included in the artifact

The `ReverseProxy` `web.config` (reverse proxy rules) and WinSW service definition are both
**generated from parameters by the script at deployment time**, rather than being templates stored
in the artifact. The artifact is therefore environment-independent, and the same build output can
be deployed to any environment. Because every environment's configuration is generated by the
same code, the configurations do not drift.

Generated files are written to the payload directory before it is mirrored, so they are ordinary
payload files. They do not need to be excluded from `/PURGE`, are included in backups, and are
restored with the configuration actually used by that version during rollback.

The service is **reinstalled**, not merely restarted, during every deployment. WinSW registers the
environment variable block and image path only when it creates the service; calling `start` alone
would not apply a changed port or environment name.

### Runtime requirements

Common requirements:

- Windows PowerShell 5.1, running as an administrator.
- IIS and the `WebAdministration` module installed on the Windows host.
- An execution account that can manage IIS, file ACLs, and Windows Firewall.
- An application health endpoint that returns HTTP 200.

`AspNetCore` additionally requires the ASP.NET Core Hosting Bundle.

`ReverseProxy` additionally requires:

- **URL Rewrite** and **Application Request Routing** installed in IIS. Without them, IIS returns
  500.19 rather than reporting a startup failure, making the issue look like an application defect.
- Node.js installed on the host. By default, the script resolves an absolute path from the target
  machine's `PATH` using `Get-Command node.exe`; `-NodeExePath` can also specify it explicitly.
  WinSW receives the resolved image path and does not depend on `PATH` when starting the service.
- `winsw.exe` in the payload root. The script generates `winsw.xml` next to it. The service ID
  comes from the XML `<id>` element, so the filename is environment-independent.
- An execution account that can install and remove Windows services.

### Azure Pipelines example

The consumer convention is to publish the script as an artifact. The deployment stage consumes
only artifacts and does not check out any repository. This ensures that Integration and a later
Staging deployment execute the exact same bytes:

```yaml
- job: PublishDeploymentScriptsJob
  displayName: 'Publish Deployment Scripts'
  steps:
    - checkout: devops-shared
      path: s/devops-shared

    - task: CopyFiles@2
      inputs:
        sourceFolder: '$(Agent.BuildDirectory)/s/devops-shared/scripts/iis'
        contents: 'Deploy-IisSite.ps1'
        targetFolder: '$(Build.ArtifactStagingDirectory)/deployment-scripts'

    - task: PublishPipelineArtifact@1
      inputs:
        targetPath: '$(Build.ArtifactStagingDirectory)/deployment-scripts'
        artifactName: 'deployment-scripts'
```

`CopyFiles@2` has no `failOnEmptySource` option, so adding a step that asserts the file exists before
publishing is recommended. Otherwise, moving the script within devops-shared would produce an empty
artifact, and the problem would surface only as a missing file during deployment.

Deployment stage:

```yaml
- download: current
  artifact: 'deployment-scripts'

- task: PowerShell@2
  displayName: 'Deploy to IIS (in-place)'
  inputs:
    targetType: filePath
    filePath: '$(Pipeline.Workspace)/deployment-scripts/Deploy-IisSite.ps1'
    arguments: >-
      -SiteName "RichillCapital.Identity.Web.Integration"
      -Port 12000
      -EnvironmentName "Integration"
      -SourcePath "$(Pipeline.Workspace)/RichillCapital.Identity.Web"
      -Version "$(version)"
      -Mode InPlace
      -HealthTimeoutSeconds 180
      -AdditionalIdentities "svc-az-agent"
    errorActionPreference: stop
    # The WebAdministration provider used by the script is not natively available under pwsh.
    pwsh: false
```

For a Node service, also pass the hosting model and loopback port:

```yaml
      -Mode InPlace
      -HostingModel ReverseProxy
      -NodePort 13999
      -CommitSha "$(Build.SourceVersion)"
```

If the target IIS server is remote, first compress the publish output into a `.zip` file. Transfer
the zip and `Deploy-IisSite.ps1` to the host, then run the same command with
`powershell.exe -File`.

> `SSH@0` splits `commands` on newlines and `;`, even inside quotes. A remote command must therefore
> be a single statement rather than a multi-statement PowerShell one-liner.

### Parameters

| Parameter | Default | Description |
|---|---|---|
| `SiteName` | Required | Name of the IIS website, application pool, and Windows service |
| `Port` | Required | External HTTP binding port |
| `EnvironmentName` | Required | Value of `ASPNETCORE_ENVIRONMENT` or `NODE_ENVIRONMENT` |
| `SourcePath` | Required | Publish output directory or `.zip` file |
| `Version` | Required | Deployment version and part of the release name |
| `Mode` | `InPlace` | `InPlace` or `Swap` |
| `HostingModel` | `AspNetCore` | `AspNetCore` or `ReverseProxy` |
| `NodePort` | `0` | Required for `ReverseProxy`; loopback port on which the Node process listens |
| `NodeExePath` | `''` | Resolved from the target machine's `PATH` when empty; can also specify the absolute path to node.exe used by WinSW |
| `ServerEntryPoint` | `server.js` | Service entry point relative to the payload root |
| `CommitSha` | `''` | Provided to the `ReverseProxy` application through `COMMIT_SHA` |
| `BuildTimeUtc` | `''` | Provided to the `ReverseProxy` application through `BUILD_TIME_UTC` |
| `SiteRoot` | `C:\inetpub\wwwroot\<SiteName>` | Site root directory |
| `HealthPath` | `/healthz` | Endpoint checked after deployment |
| `HealthTimeoutSeconds` | `120` | Number of seconds to wait for the health check; set to `0` to skip |
| `RetainReleases` | `5` | Number of previous releases retained in `Swap` mode, excluding the current version |
| `AdditionalIdentities` | `@()` | Additional accounts granted Modify permission on the site root |
| `SkipFirewallRule` | `$false` | Skips creation of the Windows Firewall inbound rule |

`AspNetCore` ignores `CommitSha` and `BuildTimeUtc` because this model embeds the information in the
assemblies during publishing.

### Deployment modes

`InPlace` takes the site offline with `app_offline.htm`, stops the application pool (and the Windows
service for `ReverseProxy`), backs up the existing payload to `<SiteRoot>.backup`, and mirrors the
new payload. The `logs` and `releases` directories are not removed. If the health check fails, the
backup is restored. This mode involves brief downtime and is suitable for Integration.

`Swap` publishes the payload to `<SiteRoot>\releases\<version>_<timestamp>` and points the release's
`logs` junction to `<SiteRoot>\logs`. After switching the IIS physical path, the script runs the
health check. On failure, it switches back to the previous valid release; on success, it removes
old releases beyond the retention limit. This mode is suitable for environments that require fast
rollback.

Backup and rollback require the target directory to contain the payload marker for the selected
hosting model (`web.config` or `server.js`). No previous payload exists during the first deployment,
so a failed health check fails the deployment rather than rolling back to an empty directory.

## Local validation

```powershell
Invoke-ScriptAnalyzer -Path scripts -Recurse -Settings ./PSScriptAnalyzerSettings.psd1
Invoke-Pester -Path ./tests
```

GitHub Actions runs the same static analysis and tests for pushes and pull requests to `master`.

The tests perform AST-based static analysis. Helper functions currently reside in the same file as
the deployment logic, and dot-sourcing it would execute the entire script, so they cannot be tested
in isolation. Adding behavioral tests requires first extracting the helpers into a file that can
be dot-sourced, such as `scripts/iis/_IisCommon.ps1`. All helper inputs are now explicit parameters
and no longer depend on the script's dynamic scope, so extracting them will not pull the entire
scope along.
